# Spotify Tracks: практика MongoDB

Навчальний проєкт на датасеті [Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset) (~114 тис. треків). Дані завантажуються в MongoDB Atlas, трансформуються в зручну структуру, після чого над ними виконуються аналітичні запити.

## Структура проєкту

| Файл | Призначення |
|---|---|
| `scripts/01_load_data.py` | Завантаження CSV у колекцію `tracks_raw` (pymongo, батчами по 1000) |
| `scripts/02_transform.js` | Трансформація `tracks_raw` → `tracks` через aggregation pipeline |
| `queries/part2_queries.js` | Чотири запити разом з explain |
| `queries/create_indexes.js` | Індекси до запитів |


## Структура документа в колекції `tracks`
 
```js
{
  track_id, track_name, album_name, explicit, popularity, duration_ms, track_genre,
  artists: ["Artist 1", "Artist 2"],          // масив рядків
  audio_features: {                           // вкладений об'єкт
    danceability, energy, loudness, speechiness, acousticness,
    instrumentalness, liveness, valence, tempo, key, mode, time_signature
  },
  duration_sec,                               // duration_ms / 1000, 1 знак після коми
  popularity_tier                             // "high" (>=70) | "medium" (>=40) | "low"
}
```
 
## Запуск

Ініціалізуємо БД:

```bash
mongosh "ВАШ_URI" --file scripts/01_load_data.py
```

Трансформуємо Датасет:

```bash
mongosh "ВАШ_URI" --file scripts/02_transform.js
```

Виконуємо запит explain з директорії queries (якщо потрібент тільки результат запиту то коментуємо поле explain):

```bash
mongosh "ВАШ_URI" --file queries/part2_queries.js
```
 
Тепер створюємо індекси:

```bash
mongosh "ВАШ_URI" --file queries/create_indexes.js
```

Та повторно запускаємо part2_queries.js

# Відповіді на питання

1. **Чому audio_features винесені у вкладений об'єкт:**

- Логічне групування. 12 технічних полів складають одну смислову сутність. Верхній рівень документа залишається чистим: ідентифікація та метадані окремо, аудіоаналіз окремо.
- Зручна робота з блоком як цілим. Його можна одним полем проєктувати ({ audio_features: 1 }), передавати у застосунок або оновлювати цілком;    
- Немає конфліктів назв і легко додавати нові характеристики;

**Коли вигідно:** поля завжди читаються разом, мають спільний життєвий цикл (наприклад, приходять з одного API), а документ має чітку структуру.

**Коли створює проблеми:**

- Потрібна dot-нотація: "audio_features.energy", а індекси треба створювати на { "audio_features.energy": 1 };
- Часткове оновлення вкладених полів вимагає $set з крапкою, а $set: { audio_features: {...} } перезапише весь об'єкт;
- Пошук по об'єкту як цілому ({ audio_features: {...} }) вимагає точного збігу, включно з порядком полів, тому майже не використовується;
- Якщо поля потрібні окремо й дуже часто (наприклад, лише energy у кожному запиті), вкладення дає лише зайвий синтаксис без вигоди.

2. **Чому artists це масив, а не рядок:** один трек може мати кількох виконавців, а MongoDB має нативну підтримку масивів, зокрема для індексів і запитів.

**Що стає простішим:**

- Пошук треків виконавця: db.tracks.find({ artists: "Drake" }) замість { artists: /Drake/ }, який шукає підрядок, повільний і дає хибні збіги (наприклад, “Drake” знайде “Drake Bell”);
- Індексація: multikey-індекс { artists: 1 } дає швидкий точний пошук;
- Колаборації: { artists: { $all: ["Drake", "Future"] } } для треків, де є обидва виконавці;
- Кількість виконавців: { artists: { $size: 2 } };
- Агрегації по виконавцях: $unwind: "$artists" + $group дає статистику на одного виконавця (кількість треків, середня популярність), чого з рядком без парсингу не зробити.

# Індекси та оцінювання продуктивності
 
### Методика
 
1. `part2_queries.js` виконує `explain("executionStats")` для чотирьох запитів без індексів. У колекції `tracks` на цей момент є лише індекс `_id_`.
2. `create_indexes.js` створює індекси під запити.
3. `part2_queries.js` запускається повторно.
Повні результати explain зберігаються в колекції `spotify.explain_results`, а ключові метрики порівнюються нижче. У датасеті після очищення 113 999 документів.


### Створені індекси
 
| Індекс | Ключ | Для запиту |
|---|---|---|
| `idx_q1_party` | `audio_features.danceability`, `audio_features.energy`, `duration_ms` | 1 |
| `idx_q4_focus` | `explicit`, `audio_features.instrumentalness`, `audio_features.loudness`, `audio_features.speechiness` | 4 |
| `idx_q2_artists` | `artists`, `popularity` | 2 |
| `idx_q3_genre_tempo` | `track_genre`, `audio_features.tempo` | 3 |
 
### Результати вимірів
 
| Запит | План до | План після | `totalDocsExamined` | `totalKeysExamined` | `nReturned` | Час, мс |
|---|---|---|---|---|---|---|
| 1. Вечірка | COLLSCAN | **IXSCAN** (`idx_q1_party`) | 113 999 → **7 311** | 0 → 11 278 | 7 311 | 210 → **40** |
| 2. Популярні артисти | COLLSCAN | COLLSCAN | 113 999 → 113 999 | 0 → 0 | 113 999 | 491 → 324 |
| 3. Викиди за темпом | COLLSCAN | COLLSCAN | 113 999 → 113 999 | 0 → 0 | 114 | 964 → 622 |
| 4. Фонове прослуховування | COLLSCAN | **IXSCAN** (`idx_q4_focus`) | 113 999 → **9 324** | 0 → 10 512 | 8 311 | 137 → **109** |
 
Примітка до `nReturned`: це кількість документів, які віддав крок сканування (для запиту 2 це всі документи колекції, для запиту 3 це 114 груп-жанрів, для запиту 4 це документи, що пройшли `$match`, до видалення дублів за `track_id`).

### Висновки
 
- Індекси дають відчутний ефект там, де запит має вибірковий фільтр (запити 1 і 4): читання документів падає на понад 90%, а час виконання зменшується від 20% до 80% залежно від того, яка частина часу припадає на фільтр.
- Для агрегацій по всій колекції (запити 2 і 3) індекс не допомагає: `$group` без попереднього `$match` потребує всіх документів. Тут оптимізувати варто структурою даних або попередньо обчисленими колекціями (наприклад, через `$merge`).
- У складеному індексі порядок полів і тип умов (рівність, діапазон) визначають, наскільки ефективно обмежується сканування.
- Індекси мають ціну: додаткове місце на диску та повільніші вставки й оновлення, оскільки кожен індекс оновлюється разом з документом. Невикористані `idx_q2_artists` і `idx_q3_genre_tempo` варто видалити (`db.tracks.dropIndex("idx_q2_artists")`).
